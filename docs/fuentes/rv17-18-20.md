### RV17-F-01 — Sintaxis y semántica de `EXCLUDE` (exclusion constraints) en `CREATE TABLE`
- **Título:** CREATE TABLE — sección EXCLUDE
- **Editor:** PostgreSQL Global Development Group
- **URL:** https://www.postgresql.org/docs/current/sql-createtable.html
- **Fecha publicada/actualizada:** no consta versión específica en el contenido extraído (documentación viva, rama "current")
- **Fecha de consulta:** 2026-09-05
- **Cita textual:** "The EXCLUDE clause defines an exclusion constraint, which guarantees that if any two rows are compared on the specified column(s) or expression(s) using the specified operator(s), not all of these comparisons will return TRUE. If all of the specified operators test for equality, this is equivalent to a UNIQUE constraint, although an ordinary unique constraint will be faster. However, exclusion constraints can specify constraints that are more general than simple equality... The operator(s) are required to be commutative." Y sobre el método de acceso: "the access method will always be GiST or SP-GiST" (GIN queda excluido porque el constraint requiere `amgettuple`). Ejemplo canónico citado en la página: `CREATE TABLE circles (c circle, EXCLUDE USING gist (c WITH &&));`.
- **Alcance:** respalda directamente el diseño del invariante central de RV17 (no solapamiento de reservas/bloqueos por unidad) usando `EXCLUDE USING gist`. El ejemplo verbatim de la página es de tipo `circle` con `&&`, no un ejemplo con múltiples columnas (igualdad + rango) — ese patrón multi-columna se confirma en RV17-F-02.
- **Confianza:** alta (cita verbatim de documentación oficial).
- **Laguna:** ninguna relevante; se advierte que el ejemplo de esta página específica no combina igualdad de `unit_id` con solapamiento de rango — ese ejemplo combinado proviene de la documentación de `btree_gist` (RV17-F-02), no de esta página.

### RV17-F-02 — Módulo `btree_gist` y ejemplo de `EXCLUDE` con igualdad + no-igualdad/rango
- **Título:** F.7. btree_gist — B-tree Equivalent GiST Operator Classes
- **Editor:** PostgreSQL Global Development Group
- **URL:** https://www.postgresql.org/docs/current/btree-gist.html
- **Fecha de consulta:** 2026-09-05
- **Cita textual:** "btree_gist provides GiST index operator classes that implement B-tree equivalent behavior for the data types int2, int4, int8, float4, float8, numeric, timestamp with time zone, timestamp without time zone, time with time zone, time without time zone, date, interval, oid, money, char, varchar, text, bytea, bit, varbit, macaddr, macaddr8, inet, cidr, uuid, bool and all enum types." Y el ejemplo de exclusion constraint que combina dos operadores en la misma cláusula: `CREATE TABLE zoo (cage INTEGER, animal TEXT, EXCLUDE USING GIST (cage WITH =, animal WITH <>));` (constraint que impide más de un tipo de animal por jaula, combinando `=` en `cage` con `<>` en `animal`).
- **Alcance:** confirma dos cosas necesarias para RV17: (1) `btree_gist` extiende GiST para soportar tipos "normales" (enteros, uuid, etc.) con operadores de igualdad, lo cual es la pieza que falta para poder escribir `EXCLUDE USING gist (unit_id WITH =, during WITH &&)` — sin `btree_gist`, GiST no sabría indexar `unit_id` (tipo `uuid`/`integer`) para el operador `=`; (2) el patrón documentado oficialmente de combinar un operador de igualdad con un segundo operador en la misma cláusula EXCLUDE, que es exactamente la forma que necesita el constraint `unit_id WITH =, during WITH &&` de RV17 (aunque el ejemplo oficial usa `<>` sobre texto, no `&&` sobre un rango, el mecanismo — múltiples `exclude_element ... WITH operator` separados por coma dentro del mismo `EXCLUDE USING gist(...)` — es el mismo que exige la sintaxis descrita en RV17-F-01).
- **Confianza:** alta (cita verbatim de documentación oficial).
- **Laguna:** la página no muestra, en el fragmento extraído, un ejemplo literal que combine `=` con `&&` sobre un `daterange`/`tstzrange` específicamente (combina `=` con `<>` sobre texto). El ejemplo de `unit_id WITH =, during WITH &&` propuesto en RV17-arquitectura-datos.md es una composición razonada a partir de la sintaxis confirmada en RV17-F-01 (EXCLUDE acepta múltiples `exclude_element WITH operator` separados por coma) y de la cobertura de tipos de `btree_gist` (RV17-F-02, que sí incluye `date`/`timestamp` — se listan explícitamente— y por extensión el propio módulo documenta soporte de igualdad sobre tipos escalares comunes usados como clave de agrupación como `unit_id`), no una cita literal de un ejemplo idéntico. Se marca explícitamente como composición, no como cita de un ejemplo preexistente idéntico, y se recomienda validar con `\d+` o un `EXPLAIN` real en una base de prueba antes de considerarlo verificado end-to-end en producción.

### RV17-F-03 — Nivel de aislamiento SERIALIZABLE
- **Título:** 13.2. Transaction Isolation — sección Serializable Isolation Level
- **Editor:** PostgreSQL Global Development Group
- **URL:** https://www.postgresql.org/docs/current/transaction-iso.html
- **Fecha de consulta:** 2026-09-05
- **Cita textual:** "The Serializable isolation level provides the strictest transaction isolation. This level emulates serial transaction execution for all committed transactions; as if transactions had been executed one after another, serially, rather than concurrently." Sobre reintentos: "applications using this level must be prepared to retry transactions due to serialization failures." Sobre el error concreto: `ERROR: could not serialize access due to read/write dependencies among transactions` (SQLSTATE `40001`). Sobre bloqueo de predicados: "To guarantee true serializability PostgreSQL uses predicate locking... these locks do not cause any blocking and therefore can not play any part in causing a deadlock." Advertencia importante citada: "it is possible to see unique constraint violations caused by conflicts with overlapping Serializable transactions even after explicitly checking that the key isn't present before attempting to insert it."
- **Alcance:** respalda la recomendación de RV17 de que, aun con el exclusion constraint como barrera dura contra solapamientos, cualquier flujo aplicativo que primero "consulte disponibilidad" y luego "inserte la reserva" en pasos separados debe correr dentro de una transacción `SERIALIZABLE` (o aceptar el fallo del `EXCLUDE` como mecanismo primario) y estar preparado para reintentar ante `40001` — el constraint de exclusión es la garantía de integridad de datos; `SERIALIZABLE` es un refuerzo a nivel de lógica de negocio cuando hay lecturas previas a la escritura que no pasan por el propio constraint.
- **Confianza:** alta (cita verbatim de documentación oficial).
- **Laguna:** ninguna relevante para el alcance de RV17.

### RV17-F-04 — Bounds de range types (`[`, `)`, forma canónica de `daterange`)
- **Título:** 8.17. Range Types — secciones 8.17.3 (Inclusive and Exclusive Bounds), 8.17.6 (Constructing Ranges) y 8.17.7 (Discrete Range Types)
- **Editor:** PostgreSQL Global Development Group
- **URL:** https://www.postgresql.org/docs/current/rangetypes.html
- **Fecha de consulta:** 2026-09-05
- **Cita textual:** "In the text form of a range, an inclusive lower bound is represented by '[' while an exclusive lower bound is represented by '('. Likewise, an inclusive upper bound is represented by ']', while an exclusive upper bound is represented by ')'." Sobre construcción: "The two-argument form constructs a range in standard form (lower bound inclusive, upper bound exclusive)... If the third argument is omitted, '[)' is assumed." Sobre tipos discretos: "The built-in range types int4range, int8range, and daterange all use a canonical form that includes the lower bound and excludes the upper bound; that is, '[)'." Lista de tipos incluida en la página: `tsrange`, `tstzrange`, `daterange` (entre otros), cada uno con su multirange correspondiente.
- **Alcance:** respalda directamente por qué `daterange` es el tipo natural para modelar `[check_in, check_out)` en RV17: su forma canónica YA es semiabierta `[)`, de modo que un check-out el mismo día que un check-in de otra reserva (mismo valor de frontera) no se considera solapamiento — los rangos `[2026-09-10, 2026-09-15)` y `[2026-09-15, 2026-09-20)` son adyacentes, no solapados, bajo esta semántica. Para `tstzrange` (cuando se necesita hora exacta), la forma canónica NO es forzada automáticamente por PostgreSQL de la misma manera que en los tipos discretos (`tstzrange` es continuo, no discreto), por lo que el bound debe especificarse EXPLÍCITAMENTE como `[)` al construir el valor (p. ej. `tstzrange(check_in, check_out, '[)')`), o el diseño corre el riesgo de que dos reservas con checkout/checkin en el mismo instante exacto se traten de forma inconsistente si alguien construye el rango con bounds por defecto distintos.
- **Confianza:** alta (cita verbatim de documentación oficial).
- **Laguna:** la página no fue citada aquí sobre el comportamiento de igualdad de instantes exactos en `tstzrange` con precisión de microsegundos (p. ej. si checkout de A y check-in de B son literalmente el mismo `timestamptz`, un `[)` en ambos rangos los deja adyacentes y no solapados — esto se infiere de la semántica general de bounds citada, no de un ejemplo específico con `tstzrange` en la página).

### RV17-F-05 — Row Level Security (RLS): `ENABLE ROW LEVEL SECURITY`, políticas, dueños de tabla
- **Título:** 5.9. Row Security Policies
- **Editor:** PostgreSQL Global Development Group
- **URL:** https://www.postgresql.org/docs/current/ddl-rowsecurity.html
- **Fecha de consulta:** 2026-09-05
- **Cita textual:** "When row security is enabled on a table (with ALTER TABLE ... ENABLE ROW LEVEL SECURITY), all normal access to the table for selecting rows or modifying rows must be allowed by a row security policy. (However, the table's owner is typically not subject to row security policies.) If no policy exists for the table, a default-deny policy is used, meaning that no rows are visible or can be modified." Sobre `WITH CHECK` implícito: "The policy above implicitly provides a WITH CHECK clause identical to its USING clause, so that the constraint applies both to rows selected by a command... and to rows modified by a command." Sobre superusuarios y dueños: "Superusers and roles with the BYPASSRLS attribute always bypass the row security system when accessing a table. Table owners normally bypass row security as well, though a table owner can choose to be subject to row security with ALTER TABLE ... FORCE ROW LEVEL SECURITY." Ejemplo citado: `CREATE POLICY user_policy ON users USING (user_name = current_user);`.
- **Alcance:** respalda el diseño de RLS de RV17 (una política por tabla con `tenant_id`, verificada con `USING`/`WITH CHECK`, y la necesidad explícita de `FORCE ROW LEVEL SECURITY` si algún rol propietario de las tablas ejecuta consultas de aplicación — riesgo real si el rol de conexión del backend es también el dueño del esquema). Importante: la documentación oficial NO obliga a un nombre de función específico (`current_tenant_ids()` es un patrón de convención del proyecto hermano de Hoteles, no un requisito de PostgreSQL) — cualquier expresión booleana es válida en `USING`.
- **Confianza:** alta (cita verbatim de documentación oficial).
- **Laguna:** ninguna relevante; el ejemplo con función `security definer` multi-tenant (`is_restaurant_staff`) no proviene de esta página sino del código real del proyecto hermano `atiende-restaurantes` (ver RV17-F-09).

### RV17-F-06 — Patrón Transactional Outbox
- **Título:** Pattern: Transactional outbox
- **Editor:** Chris Richardson, microservices.io
- **URL:** https://microservices.io/patterns/data/transactional-outbox.html
- **Fecha de consulta:** 2026-09-05
- **Cita textual:** Problema formulado explícitamente en la página: "How to atomically update the database and send messages to a message broker?" Solución: "The solution is for the service that sends the message to first store the message in the database as part of the transaction that updates the business entities. A separate process then sends the messages to the message broker." Componentes citados: "Message outbox - if it's a relational database, this is a table that stores the messages to be sent... Message relay - sends the messages stored in the outbox to the message broker."
- **Alcance:** respalda directamente por qué RV17 necesita una tabla outbox transaccional para "escribir el evento de reserva + encolar el mensaje de sync hacia el canal" de forma atómica: si el commit de `reservation_events`/`reservation` y el envío del mensaje al canal (Airbnb/Booking) fueran dos pasos independientes sin outbox, un crash del proceso entre el commit de BD y el envío del mensaje perdería el evento de sincronización de forma silenciosa (el `INSERT` en la tabla outbox ocurre en la MISMA transacción que el cambio de negocio, así que ambos se confirman o ninguno lo hace; el "message relay" —un worker separado— es responsable de leer la tabla y publicar, con reintentos, de forma desacoplada del commit original).
- **Confianza:** alta (cita verbatim de fuente reconocida en la literatura de arquitectura de microservicios).
- **Laguna:** no se pudo acceder a la documentación de debezium.io sobre el patrón "outbox event router" (dos URLs distintas de debezium.io devolvieron HTTP 403 Forbidden al intentar el fetch en esta sesión — ver sección de Lagunas del documento principal). El diseño de RV17 usa solo el patrón conceptual de microservices.io (outbox + worker relay propio hecho a mano vía polling/`SELECT ... FOR UPDATE SKIP LOCKED` o `LISTEN/NOTIFY`), NO asume Debezium/CDC como componente obligatorio — eso queda como opción no verificada en esta sesión, a evaluar en un módulo de infraestructura posterior si el volumen lo justifica.

### RV17-F-11 — Advisory Locks (`pg_advisory_lock`/`pg_advisory_xact_lock`): alcance de sesión vs. transacción
- **Título:** 13.3.5. Advisory Locks (sección de Explicit Locking)
- **Editor:** PostgreSQL Global Development Group
- **URL:** https://www.postgresql.org/docs/current/explicit-locking.html
- **Fecha de consulta:** 2026-09-05
- **Cita textual:** "PostgreSQL provides a means for creating locks that have application-defined meanings. These are called advisory locks, because the system does not enforce their use — it is up to the application to use them correctly." Sobre el alcance transaccional: "Transaction-level lock requests... behave more like regular lock requests: they are automatically released at the end of the transaction, and there is no explicit unlock operation. This behavior is often more convenient than the session-level behavior for short-term usage of an advisory lock." Y sobre el nivel de sesión (para contraste): "Once acquired at session level, an advisory lock is held until explicitly released or the session ends."
- **Alcance:** respalda el uso de `pg_advisory_xact_lock` en §7.4 de RV17-arquitectura-datos.md para serializar el procesamiento de eventos concurrentes sobre la misma `unidad_id`/`propiedad_id`: al ser de alcance transaccional, se libera automáticamente al terminar la transacción del worker, sin requerir un `unlock` explícito ni riesgo de dejar el lock retenido si el proceso falla dentro de la misma transacción.

### RV20-F-01 — Definición de Span, SpanContext y jerarquía de traza (parent/child, TraceId compartido)
- **Título/editor:** OpenTelemetry Specification — Tracing API
- **URL:** https://opentelemetry.io/docs/specs/otel/trace/api/
- **Fecha de publicación:** no consta versión/fecha exacta en el contenido extraído (especificación viva, versionada en el repo de OTel)
- **Fecha de consulta:** 2026-09-05
- **Cita textual:** "Each trace contains a root span, which typically describes the entire operation and, optionally, one or more sub-spans for its sub-operations." Y: "For a Span with a parent, the `TraceId` MUST be the same as the parent."
- **Alcance:** fundamenta el diseño de traza distribuida webhook→cola→worker→escritura→confirmación como una única traza (mismo TraceId) con spans hijos, incluso cuando el span "remoto" cruza un proceso worker distinto (IsRemote=true en el SpanContext heredado).
- **Confianza:** alta (documentación oficial, citas literales).
- **Laguna:** ninguna relevante a este uso.

### RV20-F-02 — SpanKind: PRODUCER/CONSUMER para flujos asíncronos (cola)
- **Título/editor:** OpenTelemetry Specification — Tracing API
- **URL:** https://opentelemetry.io/docs/specs/otel/trace/api/
- **Fecha de consulta:** 2026-09-05
- **Cita textual:** "PRODUCER: describes the initiation or scheduling of a local or remote operation" que "often ends before the correlated `CONSUMER` span"; "CONSUMER: represents the processing of an operation initiated by a producer, where the producer does not wait."
- **Alcance:** justifica marcar el encolado del webhook entrante como span PRODUCER (encolar y terminar) y el procesamiento del worker como span CONSUMER (no bloquea al productor) — exactamente el patrón webhook→cola→worker del calendario unificado.
- **Confianza:** alta.
- **Laguna:** ninguna.

### RV20-F-03 — Status de span (Ok/Error/Unset) para marcar fallos de sync sin inventar estado
- **Título/editor:** OpenTelemetry Specification — Tracing API
- **URL:** https://opentelemetry.io/docs/specs/otel/trace/api/
- **Fecha de consulta:** 2026-09-05
- **Cita textual:** "Unset: The default status"; "Error: The operation contains an error"; jerarquía "Ok > Error > Unset."
- **Alcance:** fundamenta que un span de sincronización que no puede confirmarse (timeout, feed caído) debe quedar en `Unset`/`Error`, nunca marcarse `Ok` por omisión — coherente con el principio de LAGUNAS.md línea 171 ("feed inaccesible ≠ calendario vacío", responsabilidad de RV20).
- **Confianza:** alta.
- **Laguna:** ninguna.

### RV20-F-04 — Tipos de instrumento de métricas: Counter, UpDownCounter, Histogram
- **Título/editor:** OpenTelemetry Specification — Metrics API
- **URL:** https://opentelemetry.io/docs/specs/otel/metrics/api/
- **Fecha de consulta:** 2026-09-05
- **Cita textual:** "Counter is a synchronous Instrument which supports non-negative increments" (ej. "count the number of HTTP 5xx errors"); "Histogram is a synchronous Instrument which can be used to report arbitrary values that are likely to be statistically meaningful" (ej. - **Alcance:** fundamenta el mapeo directo de métricas RV20 a instrumentos OTel: `sync_errores_total` → Counter; `sync_duracion_ms` (webhook→escritura) → Histogram; `cola_profundidad` (mensajes pendientes en la cola) → UpDownCounter.
- **Confianza:** alta.
- **Laguna:** ninguna.

### RV20-F-05 — Gauge asíncrono para valores no aditivos observados por muestreo (ej. edad de última sync exitosa)
- **Título/editor:** OpenTelemetry Specification — Metrics API
- **URL:** https://opentelemetry.io/docs/specs/otel/metrics/api/
- **Fecha de consulta:** 2026-09-05
- **Cita textual:** "Asynchronous Gauge is an asynchronous Instrument which reports non-additive value(s)...when the instrument is being observed" (ej. "the current room temperature").

- **Confianza:** alta.
- **Laguna:** ninguna.

### RV20-F-06 — Convenciones de mensajería: SpanKind por operación (send/process) y atributos `messaging.system`, `messaging.message.id`
- **Título/editor:** OpenTelemetry Semantic Conventions — Messaging Spans
- **URL:** https://opentelemetry.io/docs/specs/semconv/messaging/messaging-spans/
- **Fecha de consulta:** 2026-09-05
- **Cita textual:** para el span "Send" (productor): "Span kind SHOULD be PRODUCER"; para el span "Process" (consumidor): "Span kind SHOULD be CONSUMER"; atributo requerido `messaging.system`: "The messaging system as identified by the client instrumentation"; `messaging.message.id`: "A value used by the messaging system as an identifier for the message, represented as a string"; y sobre propagación: "A producer SHOULD attach a message creation context to each message."
- **Alcance:** fundamenta el esquema concreto de atributos de la traza del webhook: `messaging.system=<broker>`, `messaging.destination.name=<cola>`, `messaging.message.id=<id del evento>` propagado desde el span de encolado (PRODUCER) hasta el span de procesamiento del worker (CONSUMER), permitiendo unir ambos lados en una sola traza.
- **Confianza:** alta.
- **Laguna:** ninguna.

### RV20-F-07 — Modelo de datos de logs: Body vs. Attributes, correlación TraceId/SpanId
- **Título/editor:** OpenTelemetry Specification — Logs Data Model
- **URL:** https://opentelemetry.io/docs/specs/otel/logs/data-model/
- **Fecha de consulta:** 2026-09-05
- **Cita textual:** Body: "a value containing the body of the log record. Can be for example a human-readable string message... or it can be a structured data composed of arrays and maps of other values"; sobre correlación: "Request trace ID as defined in W3C Trace Context... Can be set for logs that are part of request processing and have an assigned trace ID"; "If SpanId is present TraceId SHOULD be also present."
- **Alcance:** fundamenta el diseño de logs sin PII: el `Body` de cada log de sincronización debe ser una plantilla fija sin interpolar datos de huésped ("sync de disponibilidad completada para unidad {unit_id}"), y la correlación con la traza se hace vía `TraceId`/`SpanId`, no incrustando identidad del huésped en el texto — el log referencia el evento, no repite su contenido.
- **Confianza:** alta para la mecánica de correlación; **media/laguna explícita** para PII (ver limitación abajo).
- **Laguna:** el modelo de datos de logs de OTel **no incluye una regla explícita sobre PII** (verificado directamente — ver también RV20-F-08 y RV20-F-09, donde tampoco se encontró una prohibición textual de PII en atributos). La política "logs sin PII" de RV20 es una decisión de producto/cumplimiento propia (alineada con RV19, LFPDPPP y con el principio de minimización de datos), no un mandato de la especificación OTel. Se declara así para no atribuir a OTel una regla que no dice.

### RV20-F-08 — Convención de nombres de atributos (namespacing, minúsculas) — sin regla explícita de PII encontrada
- **Título/editor:** OpenTelemetry Semantic Conventions — General Attribute Naming
- **URL:** https://opentelemetry.io/docs/specs/semconv/general/naming/
- **Fecha de consulta:** 2026-09-05
- **Cita textual:** "Names SHOULD be lowercase."; "Use namespacing. Delimit the namespaces using a dot character."; "Be precise. Attribute, event, metric, and other names should be descriptive and unambiguous."
- **Alcance:** fundamenta el esquema de nombres de atributos propuesto (`sync.channel_account_id`, `sync.drift_nights`, etc.), namespaced y sin texto libre de huésped en el nombre ni en valores de baja cardinalidad.
- **Confianza:** alta para naming; se confirma explícitamente que esta página **no contiene guía sobre PII/datos sensibles** (búsqueda directa en el contenido, sin resultado).
- **Laguna:** igual que RV20-F-07: la ausencia de PII en atributos es una regla propia del producto, no derivada de esta convención.

### RV20-F-09 — Atributos generales (red, servicio) — verificación adicional de ausencia de guía de sensibilidad de datos
- **Título/editor:** OpenTelemetry Semantic Conventions — General Attributes

- **Laguna:** ninguna adicional a la ya declarada en RV20-F-07/RV20-F-08.
